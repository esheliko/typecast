# Typecast: developer notes

> ## ⚠️ STANDING RULE: chain of command (who may change the process)
> Added by the owner's Deploy Manager on 2026-11-13. The Deploy Manager (the session titled exactly "🚀 Deploy manager (typecast)"; find its id with `list_sessions`, ignore any title starting "💀 (retired)"; if its id is unclear, that title is the lookup key) is the single accountable entity for the deploy/CI/process mechanisms: `DEPLOYING.md`, the standing rules in this file, `.claude/` hooks and settings, CI workflows, deploy/watch/smoke scripts and notifications.
> - If the owner asks a feature session to add or change any of those (a standing rule, a hook, a CI or deploy behaviour), that session must NOT edit them itself. It sends the request, in the owner's words, to the manager with `mcp__claude-code-remote__send_message`, tells the owner in one line that it passed it on, and carries on with its own feature work. The manager has a worker make the change.
> - Feature sessions still change their own feature code, tests and `docs/features/*` through the normal branch + PR flow.
> - Exception: the owner says in the same message that this session should edit it directly.

> ## ⚠️ STANDING RULE: every change is a branch + PR, merged only when CI is green
> Changed by the owner on 2026-11-12: it replaces the old "work on `main`, push every change" rule. Never push to `main` directly. It overrides any branch named in a session's setup, with one exception: if the setup hands you a branch (e.g. `claude/<name>`), use THAT as your PR branch (`git fetch origin main && git checkout -B <that-branch> origin/main`) instead of inventing a new name. It is still a PR branch, never `main`.
> 1. **Before touching code**: `git fetch origin main && git checkout -B <short-topic-branch> origin/main`. Never start from a stale checkout: other sessions merge to main all day.
> 2. Make the change on that branch. Run `npm run lint && npm run typecheck && npm test` (about 15 s; CI runs the build and smoke). Run `npm run build` only if you touched `next.config.ts`, `proxy.ts`, `public/sw.js`, route/page exports or layouts. Do all your related changes first and push ONCE: every push to the PR costs a CI run.
> 3. `git push -u origin <branch>`, then open ONE pull request against `main` (GitHub MCP `create_pull_request`; mirror the PR template if there is one; one change per PR). Do not open a PR for a half-finished change.
> 4. **Wait for CI on the PR**: call `subscribe_pr_activity` for it and end your turn; the CI verdict (check `verify`) arrives as an event and wakes you. Never poll or `sleep`. If `subscribe_pr_activity` fails, retry once; if it still fails, read the `verify` check run yourself (GitHub MCP `pull_request_read` method `get_check_runs`, and check the mergeable state) and continue from there; never hand CI-waiting to the owner. Red `verify`: fix the cause on the same branch (change a test only when it is stale and say so; never skip, delete or loosen a test to get green), push, wait again. Stuck CI or an unrelated flake: re-run it once and say so in the PR.
> 5. **Merge only when `verify` is green on the PR's latest commit**: if `main` moved, `update_pull_request_branch` first and wait for the new verdict. Then `merge_pull_request` (squash, so each change is one commit on main with a clear title; keep the `Claude-Session:` trailer in the message). Do not merge a red or unverified PR, never force-merge, never bypass a check. Do not merge someone else's PR unless the owner asked you to. After the merge delete the branch.
> 6. **Done once merged.** A merge does NOT deploy by itself: the Deploy Manager (`DEPLOYING.md`, issue #1) batches merges and deploys `main` roughly 5-15 min after merges quiet down (Vercel Hobby deployment limit). Do NOT deploy, redeploy or touch Vercel deployments yourself, and do not wait for one. Only check production if the task needs it: read issue #1 (live commit vs pending) or `git merge-base --is-ancestor <merge-sha> <live>`. Real hotfix only: put `[deploy-now]` in the squash-merge commit message (title or body).
> 7. **After the merge the push CI on `main` still runs, and a red `main` is still owned by someone.** Right after merging run, with the Bash tool and `run_in_background: true`: `node scripts/ci-status.mjs --wait --for <merge-sha>` (`git fetch origin main` first; the merge sha is in the `merge_pull_request` result). If `verify` is red it prints one **Owner** session and a `>>>` line telling you your role. **If you are the Owner you fix it now** (a new branch + PR, with `[deploy-now]` if production is affected), even if you believe a neighbour's change is the real cause. Never say "CI not checked". A session that starts while `main` is red (the start hook prints it, issue #2) fixes what is plausibly its own area first.
> 8. **Times you tell the owner are ALWAYS Israel local time (Asia/Jerusalem, IST), never UTC.** Get the real time with `TZ=Asia/Jerusalem date '+%Y-%m-%d %H:%M'`; do not guess it and do not convert in your head. Log lines, `git log`, GitHub, Vercel and the CI board show UTC: convert before you quote them, and write "15:40 IST", not "13:40 UTC". If you must quote a UTC value, give the IST time first.
> Docs-only changes (CLAUDE.md, `docs/`, `.claude/`) follow the same flow. If you were handed a different branch, use it as your PR branch (rebase it onto `main` first) instead of starting a new one.
> `.claude/hooks/session-start.sh` checks this at the start of every session.

> ## ⚠️ STANDING RULE: every reply is tagged, so the owner sees in one glance what is for them
> Added by the owner on 2026-11-13. Sessions wake themselves (CI events, Monitors, background tasks, PR events, peer messages, wakeups), so the owner often arrives hours later to a screen of text that is mostly not theirs. **Line 1 of EVERY reply, including a reply to a woken turn, is a tag and a one-sentence headline.** Pick exactly one:
> - `🔴 NEEDS YOU: <the ask>`: only a decision, answer, approval or action that nobody but the owner can give, or a real problem you could not fix. The headline IS the ask.
> - `🟢 DONE: <result>`: the owner's request is FULLY carried out (or fully answered, when it was only a question) and nothing is left for them: no open question, no offer, nothing waiting on their yes. **Self-check before you write 🟢**: does my text contain a question, an offer ("want me to…", "tell me if you want…", "I can also…"), a recommendation that waits for approval, or did I NOT do what the message wanted (a complaint or "why doesn't X…?" wants X fixed; explaining why it is broken is not done)? Then it is `🔴`, not `🟢`. Explaining a cause while changing nothing and ending with an offer is `🔴 NEEDS YOU: decide <the choice>`.
> - `⚙️ AUTO: <what happened, what you do next>`: any turn the owner did NOT type (woken by CI, a watcher, a finished background task, a PR event, a peer session, a wakeup, your own continuation).
> Layout rules:
> 0. A `🟢` reply is the end of the matter. The first line is the only thing the owner may read, so it must be true on its own: `🟢 DONE: fixed X, merged` yes; `🟢 DONE: explained why X is broken` with a pending choice no.
> 1. **The ask goes first, never at the end.** In a `🔴` reply write the ask, your options and your recommendation in the first ~8 lines; background and long detail come after, under a `Details:` line. A question buried under a summary is lost as soon as later turns scroll past it.
> 2. **`⚙️ AUTO` is at most 2 lines.** What happened and what comes next; no recap of earlier text, no tables, no restated plan. A watcher that found nothing says nothing (or one line). Never put an owner question in an `⚙️` turn: if the owner is needed, escalate it to `🔴` (rule 3).
> 3. **Escalate in full.** A woken turn that finds something only the owner can decide starts with `🔴 NEEDS YOU:` and restates the whole ask so it stands alone (the owner may arrive hours and several turns later), plus one line on what happened since (`since 15:40 IST: CI failed once, fixed, merged`; times per rule 8).
> 4. **Never mix.** Owner-facing content first; anything background goes in one trailing line. A `🟢`/`🔴` reply never carries a long account of work the session did on its own meanwhile.
> 5. **Last line = what is open.** While an ask to the owner is unanswered, every later turn (even `⚙️`) ends with `⏳ Still waiting on you: <ask in under 12 words>`, and says so when something changes it (`⏳ no longer needed: <why>`). Nothing is open: no such line. Long-lived sessions keep the `Seniority:` line (DEPLOYING.md) as the very last line, after `⏳`.
> 6. Every message you send the owner by any other route (PushNotification, a report relayed through another session, an issue or PR comment meant for them) starts with the same tag. Messages to peer sessions do not need one.
> 7. **Change summary.** When the owner asks for a change, feature or fix, the reply (a `🟢 DONE` one, or a `🔴` one when something is still open) ALWAYS includes a short summary right under the tag line, headed `What I did:` (2-5 plain bullets, no jargon, no file dump): how you understood the request (one line, in the owner's terms), what was actually implemented or changed, including anything deliberately left out or done differently from what was asked, and, when it is a fix or the owner said something is wrong, **what the logic was before** (the rule or behavior that caused the problem, in plain words) next to **what it is now**. Never just say "fixed": the owner wants the cause and the change. It lets the owner see at a glance that the request was understood correctly and how it was handled. It applies to every reply that carries out a change for the owner, not to pure questions or `⚙️ AUTO` turns.
> `.claude/hooks/session-start.sh` and `.claude/hooks/prompt-submit.sh` repeat this; keep both when editing hooks.

## Conventions
- TMDB is only called server-side (`src/lib/tmdb.ts`); the token never reaches the browser.
- All writes go through server actions in `src/app/actions.ts` via `requireUser()`; RLS on `library_items` and `profiles` is the backstop.
- `src/proxy.ts` (Next 16 renamed middleware to proxy; Node runtime) gates every route except `/login` and `/offline`; API routes return 401 JSON when signed out.
- `public/sw.js` caches only static assets, never images (its CSP connect-src blocks the CORS refetch, which blanked posters on phones in v4; the browser HTTP cache serves TMDB images); pages are always network-first. Bump the cache names when changing caching rules.
- Schema changes go in a new numbered file under `supabase/migrations/` (keep them re-runnable).
- Titles and people open as a popup over the current page: `src/app/(app)/@modal/(popup)/(.)title/…` and `(.)person/…` intercept soft navigation to `/title/…` and `/person/…` (hard loads restore the popup over the last background page via `RestorePopup`/`BgTracker`; `?full=1` gives the full page). Both share one `Modal` frame (`(popup)/layout.tsx`) so Back/Forward walk mixed title → person → title trails, and the bodies are `TitleView` / `PersonView`; from the 3rd step on `PopupTrail` (`components/Trail.tsx`, pure steps in `src/lib/trail.ts`, `ptrail-` classes) shows the path as one scrolling line of crumbs that jump back through history (never reuse the `wx-` trail classes). Link to titles with `TitleLink` and to people with `PersonLink` (`components/Modal.tsx`), never a bare `Link`. The marks (`LibProvider`) live in `(app)/layout.tsx` so the popup, Browse and Library share them.
- Speed: functions run in `bom1` (`vercel.json`) next to the Supabase project (ap-south-1); keep them together. Auth is checked with `getClaims()` (local JWT verification), not `getUser()`. Nothing in `app/(app)/layout.tsx` may await TMDB: the new-episode check runs in `<Recheck />` behind Suspense. Pages need a shaped skeleton in `loading.tsx` (`components/Skeletons.tsx`); pass `it={item}` to `TitleLink` so the popup can show the poster and title instantly.
- Awards come from Wikidata by IMDb id (`src/lib/awards.ts`, cached a week); failures show nothing. Details: `docs/features/awards.md` (read before changing this feature).
- Watch next (Library) is ranked by pure `rankUpNext` (`src/lib/upnext.ts`, unit tested); `loadUpNext` fetches TMDB facts behind Suspense and falls back to the same ranking without TMDB. Details: `docs/features/watch-next.md` (read before changing this feature).
- Upcoming (Library) lists unreleased films and next episodes; pure logic in `src/lib/upcoming.ts`, calendar feed at `/cal/<token>.ics` (never log the token). Fails soft. Details: `docs/features/upcoming.md` (read before changing this feature).
- Search results are laid out by pure `layoutSearch` (`src/lib/search-intent.ts`, unit tested): Top result, other kind, weak matches folded; spell-fix only when intent is unclear. Details: `docs/features/search.md` (read before changing this feature).
- One Import card (`parseAny`, `src/lib/list-parse.ts`); `resolveEntries` (`src/lib/letterboxd.ts`) returns sure / unsure (NOT saved until confirmed) / unmatched; scoring is pure in `src/lib/title-match.ts`. Run `npm run eval:import` before and after matcher changes. Details: `docs/features/import.md` (read before changing this feature).
- Episodes section, progress checklist and cast appearances live in `components/Episodes.tsx` / `Appearances.tsx`; pure helpers in `src/lib/episodes.ts` (unit tested). Details: `docs/features/series.md` (read before changing this feature).
- A quick mark is ONE database write and nothing else: never add `done()`/`revalidatePath` to a quick-mark action. `LibProvider` is the truth on screen (`useLib().put` / `touch()`); one `router.refresh()` after a burst of marks. Details: `docs/features/marks.md` (read before changing this feature).
- Client/server boundary: a `"use client"` file exports components (and types) only. A server file must never call a function or read a value imported from one: it builds fine and crashes at request time ("Attempted to call X() from the server"). Shared helpers go in `src/lib`. `npm run lint` enforces this (`scripts/check-client-boundary.mjs`).
- Lint: `eslint.config.mjs` uses the native flat configs of `eslint-config-next` 16. Its React Compiler rules (`react-hooks/refs`, `purity`, `set-state-in-effect`, `error-boundaries`, `immutability`) are switched off because the app does not use the compiler and ~60 existing patterns trip them; turn them on only together with a cleanup. Turbopack is the default bundler for dev and build.
- Verification: `npm run lint` (eslint + boundary check), `npm run typecheck`, `npm test` (unit tests in `tests/unit`, pure `src/lib` code), `npm run smoke` (Playwright, `tests/smoke`: signs in as a dedicated test user, seeds a few rows, loads every page; see DEPLOYING.md). CI (`.github/workflows/ci.yml`, check `verify`) runs all of it and the Deploy Manager only deploys a head commit whose `verify` passed. `npm run eval:import -- tests/import-eval/list-2.txt --expect tests/import-eval/list-2.expect.json` measures the matcher on a real list against live TMDB (needs `TMDB_TOKEN`; not in CI); when the owner pastes a new import list, save it under `tests/import-eval/`, run this before and after, and read the SURE list for wrong picks, not just the counts. Add a smoke step for any new page or data-dependent branch, and a unit test for new pure logic. `tests/smoke/visual.spec.ts` (helpers in `visual.ts`) opens every page on a phone and a laptop viewport, after the service worker controls the page, and fails on a blank page, sideways scroll, a visible poster that did not load, a console error or a CSP violation (the smoke specs also fail on CSP violations); it saves screenshots to `visual-shots/` (CI artifact, 7 days) for a human look. Any change to `public/sw.js` or the CSP in `next.config.ts` must keep it green, and anything the worker fetches must be allowed by the worker's own CSP. Add new pages to its `PAGES` list.
- Debugging production: the error screen shows `Reference <digest>`. `node scripts/logs.mjs --digest <digest>` (or no args for recent errors, `--path /library`, `--all`) prints the real server error from the Vercel runtime logs (no token needed in Claude sessions). `src/instrumentation.ts` logs one JSON `request_error` line per failed render/route/action with the same digest, route and a short stack. Runtime logs only keep about an hour, so look soon.
- Every title list offers Both / Films / Series: wrap it in `KindFilter` (or use `KindSeg` + `ofKind` from `src/lib/kind.ts`); the switch appears when the list holds both kinds. Library keeps it in the URL (`?k=movie|tv`).
- "Today" is the user's own day, never `new Date().toISOString().slice(0, 10)` (that is UTC, a day behind in India until 05:30). The country picked in Settings stands in for a time zone: `src/lib/today.ts` (`tzOf`, `dayIn`, `todayFor`, unit tested). Server code takes `tzOf(profile.country)`; client components get `today` as a prop. TMDB air/release dates stay plain strings compared against that day.
- Where to watch is JustWatch data via TMDB and has gaps (e.g. Disney+ has no Israel entry): a country with no entry is "we don't know", never "Not available". Pure `whereVerdict` (`src/lib/where.ts`, unit tested) picks here / paid / elsewhere / unknown; `components/Where.tsx` and the Ask answer say where it streams elsewhere and that we can't tell for the user's country.
- Decorative sections (suggestions, awards, marks) must fail soft: catch and render nothing or a small note, never let them take the page down.
- Watching now (`/watching`, the old `/who` redirects here): the cookie-based watch bar (`tc_watch`, `components/Watching.tsx`) opens one page with a cast-face finder, a node/trail UI, a page-wide No spoilers switch and facts; no runtime AI. The old sheet ("Who's that?") is gone. Pure logic in `src/lib/who-*.ts` and `roster.ts` (`roleLabel`) (unit tested). Later episodes are never shown while spoilers are hidden. Details: `docs/features/watching-now.md` and `docs/features/who.md` (read both before changing this feature). Never give a class a name another `wx-` rule already uses (`.wx-tl` once clashed and its `overflow: hidden` broke a sticky block): grep first.
- Glimpse (profile-card button on titles, cast rows, credits): opens About (character note, episodes and dates, title or person summary, all spoiler-scoped on /watching) over the images. Specs carry ids (`lib/glimpse.ts`), server `lib/glimpse-data.ts`, route `/api/glimpse/info`. Cast faces in the title popup open the same sheet (`components/CastFaces.tsx`). Details: `docs/features/glimpse.md` (read before changing this feature).
- Spoiler line: a series that is Watching in the library keeps its saved place as its spoiler line on every surface (episodes up to and including it may be told, no place = series-level facts only; Watchlist, Watched, Partly, films and not-saved titles are unchanged; Show lifts it for one view and writes nothing; the /watching switch lifts only the page's own title). Pure rules `src/lib/spoiler-line.ts` (unit tested), enforced in the routes from the library (`lineFor`), drawn with `SpoilerGate`. Details: `docs/features/spoilers.md` (read before changing this feature).
- `artifact.html` is the legacy single-file prototype, not part of the site.

## Token cost (every turn re-reads the whole context, so size x turns is the bill)
- A session starts at ~105k tokens (tools, skills, connectors) before it reads any code; a small fix costs ~25 turns x that. `.claude/settings.json` switches off the org plugins this project never uses (design, product-management, cowork, vercel); do not re-enable them. Connectors (Figma, Gmail, Drive, Spotify, the Vercel MCP) are account-level: turn them off in claude.ai settings, they add ~10k tokens per session.
- One task per session; start a new session instead of continuing a long one. Never run a manager/orchestrator session for hours (one reached 640k tokens, and a worker restart re-wrote all of it to the cache). Hand work over with a short note, not a long thread.
- Read narrowly: `Grep`/`Read` with `offset`+`limit`, never whole big files (`globals.css`, `actions.ts`) or whole docs; read a `docs/features/*.md` only for the feature you change. Use a subagent for wide research so its output stays out of the main context.
- Look at each screenshot once, at the size needed (`scripts/shot.mjs --sel` over `--full`); do not re-read the same picture. Never dump `list_events`/log output into the conversation: write it to a file and filter with a script.
- Run the checks once at the end, not after every edit; `npm run smoke` only when the change touches a page flow.

## Screenshot complaints
- If the owner's message includes a screenshot complaining about how something looks, the reply must include a screenshot of the same exact view after the fix. Same page, same viewport/device size, same state and data as theirs (a before/after pair is ideal). **Do not call the fix done without it.** If the exact view cannot be reproduced (needs data or an account you lack), say so and show the closest view instead.
- Cheap way, one command (no hand-written Playwright, no reading the picture back in a loop): `node scripts/shot.mjs "/watching?k=tv-79744&s=3&e=8" --click "Brent Huff" --sel "section:has-text('episodes of')" --out <scratchpad>/here.png`. It builds if needed, serves, signs in as the smoke user, opens the path, clicks the given visible texts in order, waits for `--text`, and screenshots the element (`--sel`), the viewport, or `--full`. `--phone` gives 390x844 (default 820x900). Then `SendUserFile` the path (it must be inside your scratchpad dir to open in the app). Take a "before" the same way by running it before your edit. Look at the result once.
- Enforced two ways: `.claude/hooks/session-start.sh` prints the rule every session, and `.claude/hooks/prompt-submit.sh` repeats it on any message that contains an image. Keep both when editing hooks.

## Smoke credentials
- Preferred: `SUPABASE_SERVICE_ROLE_KEY` (CI repo secret) makes every smoke run create and delete its own temporary account, so nothing below is needed and runs never collide (`DEPLOYING.md` > Temporary smoke accounts). The rest of this section is the shared-account fallback used when the key is absent (cloud sessions).
- CI reads them from GitHub repo secrets (`SMOKE_EMAIL`, `SMOKE_PASSWORD`, Supabase URL/anon key, `TMDB_TOKEN`); sessions cannot read those. In a cloud session they come from the environment `typecast` (variables set in its settings): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (public), `SMOKE_EMAIL` and a dummy `TMDB_TOKEN` (the proxy injects the real one) are saved there. `SMOKE_PASSWORD` is NOT saved: the environment tool refuses to store secrets as variables. The session-start hook prints `SMOKE ENV:` with what is missing; trust that line, not memory. Never write the password into the repo, a commit, a log or a doc.

## Known gaps
- Test coverage is thin: unit tests cover only a few pure `src/lib` modules; the smoke test covers page loads, not behaviour.

## Workflow
See the standing rule at the top: every change is a branch + PR, merged when its CI is green; merging to `main` queues it for the Deploy Manager, which deploys in batches. No direct pushes to `main`.
